屬性（Q7a 已定案）：

| ID | 顯示名 | 顏色 | 值 |
|---|---|---|---|
| `None` | 無 | 黑白 | 0 |
| `Intuition` | 直覺 | 紅 | 1 |
| `Logic` | 邏輯 | 藍 | 2 |
| `Insight` | 批判與創造 | 綠 | 3 |

相剋：**直覺 ↔ 邏輯互斥（0×）**，批判與創造居中（0.5×），同屬性相符（1.0×）。
這不是元素環 —— 目標的屬性代表「這個難題吃哪一種腦袋」。

> **關於「綠比較強」——我先前judgment錯了，這裡更正。**
>
> 我算過綠的期望值 0.67 > 紅藍 0.50，把它記成平衡債。**那個算法用錯了前提**：
> 它假設「隨機一張牌對上隨機一個目標」，但實際的決策是
> 「**面對這個目標，我手上哪張最好**」。在那個框架下：
>
> | 目標是紅 | 紅牌 1.0 | 綠牌 0.5 | 藍牌 0 |
> |---|---|---|---|
>
> **綠永遠不是最佳解，只是「最好的可用解」** —— 它是保險牌，紅藍是對上了更強。
> 這是健康的取捨，不是失衡。
>
> 而且探索牌組**不開放玩家自主編成**，所以「玩家會把牌組堆成綠」這個風險根本不存在。
> 剩下的只有牌組配比，那是可調的內容參數，不是機制債。
>
> （企劃補充：100% 的牌若非同屬，第一輪打出去也只是 50/50。）

### 1.6 資料庫、商店與對話氣泡（2026-08-16）

| 元件 | 職責 |
|---|---|
| `LootTable`（SO）＋`LootService` | **誰在什麼場合會出現什麼**。表 → 池 → 條目，權重隨機 |
| `CharacterData` / `CharacterDatabase`（SO） | id → 角色（名字／立繪／寒暄／閒聊） |
| `ShopPanelUI` / `ShopSlotUI` | 八格貨架，圖示＋價格＋已售出 |
| `SpeechBubbleUI` / `CharacterHitbox` | 常駐對話氣泡（bark）＋ 背景角色的隱形點擊區 |

三件事定了下來，之後不要再各自發明第二套：

1. **權重寫在表上，不寫在物品上** —— 物品的 `tags` 只說「它是什麼」
2. **難度／區域＝換一張表**，`ChestInteractable` 與商店共用同一套抽取
3. **bark 與對話樹分開** —— 氣泡是氣氛，對話框是內容

`ItemData` 因此多了 `price` 與 `tags`；`RunContext` 多了 `money`。
**錢的一切（名稱、來源、經濟）都還沒設計**，`startingMoney` 是佔位值。

商店的設定由企劃補齊了（大綱 docx 裡沒有這一節）：**移動商店、店主是冷原人商人**，
21 句台詞照原文存在 `Character_merchant.asset`。

商品三類，用詞照坎貝爾在教學裡說的 —— **消耗品、武器...以及收藏品**。
商人到處跑，但貨表**依區域替換**：漁村那張食物格多一倍、且以漁獲為主，
兩張表共用同一組武器池與收藏品池。

**收藏品是大綱〈收藏品〉表的真品 8 件**（老舊釣竿、貪婪的大口、人魚肉、螺湮御守…），
含敘述與效果，並帶品質標籤 `Common`/`Uncommon`/`Rare`，抽取配比 50/33/17。

> **品質與掉落率是兩件事**：品質屬於物品（人魚肉永遠是稀有），
> 掉落率屬於表（第一區 5%、最終區 30%）。這跟「不要把 tier 寫在物品上」不衝突，
> Slay the Spire 也是這樣切的。

⚠️ 這些收藏品的效果**幾乎都在戰鬥中生效**，所以是跨隊需求（見 §2.1）。

細節、業界依據與已驗證項目見 [Phase7_ShopAndData.md](Phase7_ShopAndData.md)；
大綱完整版讀後的系統缺口見 §3.0。

#### B 怎麼做的：轉接頭，不是搬家

`Core/PlayerVitals.cs` 是探索端存取 HP／SAN 的唯一入口。

**資料沒有搬過來** —— 它還是存在隊友的 `RunStateManager`。我方只呼叫，
**沒有改到 `Assets/Romtyui/` 的任何一個字**。搬過來的是「誰負責在 run 開始時初始化」這個責任。

> 為什麼不各存一份：只要有一條路徑忘了同步，玩家就會看到
> 「探索扣了血，進戰鬥又滿血」—— 而且不會報錯，只會慢慢對不起來。

**⚠️ SAN 在隊友的程式裡叫 `Energy`。**
`RunStateManager` 沒有任何 sanity 欄位，它的 `savedCurrentEnergy` / `savedMaxEnergy` 就是 SAN ——
證據是他自己的 log 印 `SAN {savedCurrentEnergy}/{savedMaxEnergy}`，
而 `BattleManager` 有一行註解寫「因為你要求 SAN 值不重製」（一般 energy 每回合會重置，SAN 不會）。
**這個對應只寫在 `PlayerVitals` 一個地方**，其他程式一律用 `San`。

**⚠️ 初始化會讓 `hasSavedRunState` 變 true**，那是隊友 `ApplyToBattle()` 的開關 ——
往後戰鬥開始會套用我們設的血條，而不是戰鬥自己的預設值。
**那正是「run 開始就初始化」的用意**，但數值要跟戰鬥組對一次。
`maxHp <= 0` 會被擋下並警告（寫下去的話玩家一進戰鬥就是 0 血）。

**要設定的**：`GameFlowManager.Starting Max Hp` / `Starting Max San`。
**預設是 0 ＝ 不初始化**，維持舊行為，所以不會無聲改變現況。

順帶可提：`RunStateManager.cs` 的中文註解疑似不是存成 UTF-8（讀出來是亂碼）。

**已經解鎖的**：

- `RetryPolicy.CostsHealth` / `CostsSanity` **接上了** ——
  扣不動就會說「付不起」並結案，而且**扣不死人**（扣到 0 以下一律視為付不起）。
  提示文字也會顯示現在的 HP／SAN，讓玩家判斷划不划算。
- C 一定案，深淵線事件的觸發條件（「侵蝕度 50% 以上」）才有東西可以判斷。
  **它是每尊神各一條，不是單一全域值**

### 3.0 完整版讀後：新增的系統缺口

以下全部是**大綱寫得很具體、但專案裡完全不存在**的東西。按「擋不擋得住現在的工作」排：

| 缺口 | 大綱怎麼寫的 | 影響 |
|---|---|---|
| **侵蝕度** | 深淵線事件標著「（【深淵】的侵蝕度 +5%）」「+10%」，且《海市蜃樓》的觸發條件是「侵蝕度 50% 以上」 | 這就是我一直記成「世界污染進度」的東西。**它是每尊神各一條**，不是單一全域值。事件觸發條件依賴它 |
| **收藏品效果** | 8 件全部寫好了效果（抽【深淵】卡、HP 恢復 +10%、反擊額外發動…） | 幾乎全是**戰鬥中生效**，所以是跨隊需求 |
| **米可（魔法書）** | 回收用過的牌、牌用完會重發、會吃武器牌、可查看牌庫與情報碎片 | 是**牌庫管理器＋圖鑑**。探索的補牌規則已經照這個做了，但「查看」介面沒有 |
| **隊伍（協助者）** | 「四個人的話就是上限了」＝主角＋3 名協助者 | 商人的彩蛋條件、協助者卡牌、協助者互相關係都靠它 |
| **神牌規則** | 神牌賦予武器牌力量；**一張武器牌只能被一位神明賦予**；不同神明之間有相性；使用加重 SAN 負擔；被賦予的牌不會消失 | 這是一整套裝備／詞條系統，比「特殊事件給一張牌」複雜得多 |
| **事件系統** | 「每當前進到下一張地圖，滿足條件就有概率觸發事件」「從**未觸發過**的事件中隨機」 | 需要「已觸發過」的紀錄。條件包含持有數量、時間、擊殺紀錄 |

### 3.0.0 一個發現：角色池、事件、戰利品是**同一個形狀**

（2026-08-18，回答「對話要從區域角色池隨機一個，符合條件時特定角色加入」）

這三件事拆開看是三個需求，拆到底其實是同一句話：

> **一份候選清單 → 濾掉條件不成立的 → 依權重隨機挑一個**

| | 候選 | 條件 | 不重複 |
|---|---|---|---|
| 戰利品（**已完成**） | 道具 | —— | 池內 distinct |
| **角色池**（待做） | 角色 | 「坎貝爾在隊伍」「侵蝕度 ≥ 50%」 | 不需要 |
| **事件**（待做） | 事件 | 持有物、時間、擊殺紀錄 | **未觸發過** |

`LootTable` 已經把「候選＋權重＋隨機」做完了，
`CharacterData.conditionalChatter` 已經把「條件成立才加進池子」做過一次。
**缺的只有中間那一層：條件。**

#### 所以建議：先做「條件」，不要做三套

**① `RunContext` 加一個 flags 清單**（`List<string>`）。
這一個欄位同時解決：已觸發過哪些事件、坎貝爾在不在隊伍、是不是第一次進商店。

> 「未觸發過」不需要特別做 —— 它就是「`event_xxx_done` 這個 flag 不成立」。

**② 一個小小的條件求值器**，先支援三種就夠：
持有某道具 ≥ N ／ 侵蝕度 ≥ N% ／ 某個 flag 成立。

**③ 角色池與事件池都掛上去**，形狀跟 `LootTable` 一樣：

```
CharacterPool（漁村）
├─ TagQuery [漁村]      權重 100   無條件      ← 「該區域的角色池」
└─ Item     時藏         權重 40    深淵≥50%   ← 「符合條件時特定角色加入」
```

角色本來就有 `tags`，所以「該區域的角色池」＝一次標籤查詢，跟道具用的是同一招。

#### ⚠️ 因此角色池要**跟事件系統一起做**，不要先做

單獨先做角色池的話，會為了它做一套只給角色用的條件判斷；
等事件系統來的時候再做第二套，兩套的條件語法還會不一樣。
先把條件那一層做出來，兩邊都只是薄薄一層設定。

## 4. 道具數量：`ItemStack`（2026-08-15 定案並實作）

```csharp
[Serializable]
public class ItemStack { public string id; public int count = 1; }

// RunContext
public List<ItemStack> inventory;
public int  CountOf(string id);                       // 跨疊加總
public void AddItem(string id, int count = 1);        // 同 id 併疊
public bool ConsumeItem(string id, int count = 1);    // 全有或全無
```

### 為什麼是這個結構（查證過業界做法後的結論）

業界的分界線只有一條：**這個道具有沒有「每一份各自不同」的狀態。**

- **可堆疊**（三根撬棍完全一樣）→ 用 `count`
- **不可堆疊**（耐久度、詞綴、隨機屬性）→ 每份都要是獨立實例

通用寫法是 `IsStackable()` + `Count()`，不可堆疊的 count 恆為 1。
另外，「重複清單 + 顯示時才 group」也是被認可的做法（在 GUI 層堆疊而非 model 層），
**不是偷懶** —— 多數 Unity 教學展示 `{item, quantity}` 是因為它們在做格子背包，
槽位本身就是資料模型，那個理由不適用於本專案。

### 決定性的因素：漁獲

劇情大綱裡漁夫的能力是「**隨機**獲取漁獲」。
若每條魚的 `+HP／−SAN` 數值不同，漁獲就不是可互換的東西 ——
`List<string>` 與單純的 count 都裝不下它。

遊戲是肉鴿，這類「同名但數值不同」的東西只會變多。
**`ItemStack` 能表達「三根一樣的撬棍」，反過來不行**，所以選它。

換的時機也對：`RunContext` **目前完全沒有持久化**（只有 `MetaProgressData` 用 PlayerPrefs），
所以沒有舊存檔要顧；等商店與漁獲都接上去之後呼叫點會多很多。

### 幾條實作上的約束

**① `ConsumeItem` 必須全有或全無。** 需要 3 個但只有 2 個時，不可以扣掉那 2 個再回報失敗
—— 那是這類 API 最典型的 bug，而且因為資源真的少了，重試也修不回來。
程式是先 `CountOf` 確認付得起才動手扣。

**② 允許同一個 id 出現在多疊裡。** 這是刻意的，per-instance 狀態就靠它表達。
所以 `CountOf` 與 `ConsumeItem` 都跨疊處理，不可以假設「一個 id 只有一疊」。

**③ 加 per-instance 狀態時，`AddItem` 的合併規則要跟著改。**
目前是「同 id 就併」（道具還都可互換，所以正確）；加了狀態之後必須是
「同 id **且狀態相同**才併」，否則兩條不同的魚會被併成一疊。
這條寫在 `ItemStack` 的類別註解裡。

**④ 空掉的疊要移除**，否則 `inventory` 會慢慢長滿 `count == 0` 的殘骸。

### `maxStack` 還沒做

今天多拿一把倉庫鑰匙只是浪費，不會壞任何東西。要加的時候：
欄位放 `ItemData.maxStack`，但**強制邏輯不要寫進 `RunContext`** ——
它是純資料、不該認識 `ItemDatabase`。包一層 `GameFlowManager.GrantItem(id, count)`，那裡才有資料庫。

### 已接上的顯示

重試詢問現在可以顯示剩餘數量：`{0}` 道具名、`{1}` 第幾次重試、`{2}` 還剩幾個。

> ⚠️ **既有 prefab 的文案不會自動更新** —— 改 C# 的預設值不會動到已序列化的字串。
> `chest_RequiresCheck` 的 `Retry Prompt Format` 目前是客製過的兩個佔位符版本，
> 要顯示剩餘數量的話自己把 `{2}` 加進去。少傳參數才會爆，多傳會被忽略，所以不加也不會壞。
